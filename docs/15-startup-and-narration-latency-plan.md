# Museum Companion：首次识别与朗读延迟优化方案

日期：2026-11-15（Europe/Helsinki）

代码基线：iOS 0.2.3 / build 7，`d94dff7`；需求基线：[PRD v0.4](01-product-requirements.md)。

状态：待实现方案。最初仅提交本地；2026-11-15 按用户后续要求同步 GitHub。本次仍仅更新文档，不修改运行配置或生成 IPA。

> 最新排期：用户已将 P02／BUG-02 跟随检测框修复指定为 **No.1／P0**，见 [PRD](01-product-requirements.md)。本优化方案保留，执行顺序排在跟随框修复之后；其中仅为跟随框诊断所需的耗时记录可纳入 No.1。本文仍为待实现方案，不代表已修改应用或实测提速。

## 1. 目标与范围

缩短从“开始导览／视频取流”到“听到概览第一句话”的等待，并减少后续朗读句子之间的空白。优化不能通过错误识别作品、播放固定样例冒充识别结果，或取消用户打断能力实现。

本轮只规划用户确认的四项：

1. 记录各阶段耗时，建立可复现基线。
2. 提前建立 Live 连接，概览先交付，细节后台生成。
3. 对已登记的二维画作使用本地匹配和跨帧确认，减少重复云端搜索。
4. 调整音频生成与播放调度，避免一句播完才请求下一句。

换模型另行对比，本轮不把切换 Flash-Lite 混入上述改动。保留现有 Gemini 视觉／Live 配置作为首次对照；不训练新分类模型，不扩展账号付费、通用作品库或 3D 追踪范围。

## 2. 当前流程与已知等待

以下来自代码检查，不是本次实测时长：

| 环节 | 当前行为 | 等待来源 |
|---|---|---|
| 开始取流 | 建立 DAT 会话，接收至少 8 帧后自动扫描；请求帧率 15 FPS | 设备连接、出帧及帧积累；8 帧不意味着整段固定等待 |
| 全画面搜索 | `/api/artwork-candidates` 使用整帧寻找艺术品候选 | 图片上传、模型计算和结构化结果返回 |
| 跨帧确认 | 首轮返回后再选新帧调用同一接口，首次锁定需至少两次观察，最多尝试三次 | 多次云请求串行；多候选还可能等待用户选择 |
| 作品分析 | 从原始帧裁剪作品，初始化 Vision；`/api/analyze` 一次生成概览、3–5 个细节、解释、区域和来源 ID | 完整 JSON 返回并通过校验后才加载导览，概览被细节生成挡住 |
| 语音建立 | `TourNarrator.load` 后才调用 `reconnectVoice` | iPhone 到后端的 WebSocket、后端到 Gemini Live 的连接与初始化 |
| 首次发声 | 发送概览第一句，接收 PCM，调度播放器 | 首个音频包生成、传输及实际音频输出 |
| 后续句子 | 当前句播放完成后 `advanceSentence`，再请求下一句 | 每句重新等待生成；无下一句预取 |

正常首次路径至少包括两次云端搜索、一次详细分析，再加 Live 启动与首音频生成。当前图片／语音经 iPhone → 临时 HTTPS 通道 → Mac 后端 → Google；网络路径可能影响耗时，未分段测量前不能断言瓶颈属于某个服务。

20 秒设备出帧、45 秒视觉请求和 18 秒 Live 就绪等时间是超时上限，不是正常流程中的固定延时。约 2.5 秒细节点定位等待不适用于概览首次朗读。

## 3. 优化一：建立端到端耗时记录

### 3.1 事件与指标

每次导览／扫描分配 `trace_id`，每个请求分配 `request_id`。携带会话、作品、选点及播放版本，保证重试和取消后的日志不会算到新轮次。

| 事件 | 记录位置 | 用途 |
|---|---|---|
| `tour_start`、`first_frame`、`scan_start` | iPhone | 分开设备启动与识别等待 |
| `search_request/response`，含 attempt | iPhone／后端 | 逐轮搜索耗时、轮数、输入大小和结果状态 |
| `artwork_locked`、`crop_ready` | iPhone | 锁定、原始区域裁剪及本地处理耗时 |
| `overview_request/ready`、`details_request/ready` | iPhone／后端 | 改造后分别度量两类结果；旧路径记 `analysis_request/ready` |
| `live_connect_start/ready` | iPhone／后端 | 区分客户端连接与上游 Live 初始化 |
| `narration_requested`、`first_pcm_received` | iPhone／后端 | 请求到首音频数据的时间 |
| `playback_started`、`section_finished` | iPhone | 播放器实际启动、当前段播完 |
| `cancelled`、`failed`、`confirmation_wait` | 各环节 | 分开主动取消、失败和人工选择等待 |

核心指标：

- 点击开始到首个实际播放：`playback_started − tour_start`。
- 首帧到首个实际播放：`playback_started − first_frame`，单独反映识别与生成链路。
- 概览就绪到首个实际播放：衡量语音预连接是否有效。
- 列表就绪延迟、云端搜索轮数、同作品重扫请求数。
- 相邻句／段之间的实际播放空白时长，以及打断后旧音频残留。

时间使用各进程的单调时钟。同一段耗时在本进程计算，通过 ID 对齐；不能直接相减手机、Mac 和 Google 的墙钟。后端记录请求收到、上游开始／结束及返回时间；手机 RTT 减后端处理时间只能称“网络及客户端开销估计”，不能精确归因某一跳。

`player.play()` 调用、收到 PCM、整块 `.dataPlayedBack` 回调分别是不同证据。`playback_started` 优先取播放器渲染时间或实际样本进度；若当前只能记录调度时间，字段明确命名为代理值。耳边首音延迟通过单独录音／录像验证，不能用播放器调度时间代替。

### 3.2 基线样本与记录边界

- 同一 iPhone、同一网络、同一画作素材、语言、模型和音频输出路线进行前后对比。
- 分组：真实眼镜输入／手机后摄／固定录像；冷 Live 会话／可复用连接；已登记作品／陌生作品；单作品／多作品需确认。
- 起步每个关键组至少 10 次，报告样本量、成功率、中位数、最大值；小样本 p95 只作观察，不宣称稳定分位结论。演示主要路径再累计至少 30 次。
- 失败、超时、取消、人工确认单列，不能只保留成功最快的请求。
- 日志只保留 ID、阶段、耗时、模型名、图片尺寸／字节数、状态和必要计数，不保存 Key、测试链接访问码、Cookie 或用户语音原文。

交付物：可导出的单次时间线、按阶段的汇总报告、固定素材清单及运行条件。没有基线前，不给出“已提速几倍”的结论。

## 4. 优化二：语音预连接，概览与细节分开交付

### 4.1 目标流程

```text
用户开始导览并连接后端
  ├─ 设备取流 → 作品搜索／确认 → 锁定同一作品与有效 ROI
  │                              ├─ 概览生成 → 校验 → 开始朗读
  │                              └─ 细节生成 → 校验 → 列表立即显示
  └─ 建立 Live 会话（不发声、不自动开启麦克风）→ 等待有效概览

概览结束／跳过 + 列表就绪 + 用户未改选 → 自动讲 1 号
概览期间用户选点 → 中断概览，优先讲用户所选点
```

优先实现独立概览与细节请求并行，不先引入半截 JSON 增量解析。后端新增独立契约，例如 `overview` 与 `details` 两类操作；最终路径名在实现中统一。两者绑定同一 `artwork_version`、锁定凭据、ROI 和来源上下文；返回时版本不符即丢弃。

概览只生成作品身份、必要不确定性、简短介绍及来源；细节请求生成区域、稳定 ID、三词短标题和解释。概览先返回并通过校验即可朗读，不依赖细节数量大于零。细节就绪后增量补入当前导览，不能重建整场导览导致概览重播、重连 Live 或丢失用户选择。

### 4.2 现有实现必须调整的约束

- `GlassCameraModel` 目前在 `result.details.isEmpty` 时直接报错；需要区分“细节尚未到达”“已完成但没有可靠细节”和“整个作品无效”。
- `TourNarrator.load` 当前会停止旧导览并重新连接语音；需增加增量补充细节入口，保持播放、语言和已选点状态。
- `NativeLiveVoice.connect` 当前要求完整 `MuseumGuide`；服务端 `start` 也经 `clientAnalysis` 校验，要求有效概览。预连接必须新增明确的“等待作品／上下文”协议状态，不能塞假作品或假概览绕过校验。
- Live 预连接在用户开始导览后触发；没有已验证内容前不发声，不自动开启麦克风、不上传背景音。语音连接建立失败应显示状态；重试不重新执行已经成功的视觉分析。
- 更新上下文和发送概览须有顺序保证：只有当前作品的有效概览被会话接收后才能开始播报；旧作品、旧语言的迟到音频丢弃。
- 当前 HTTP 上限是同时两项 AI 请求、每分钟 30 次。并行概览与细节需纳入并发预算、取消和优先级；概览优先，不因后台细节抢占变得更慢。统计总调用量，不能只以首音变快掩盖成本上升。
- 保留旧 `/api/analyze` 契约供旧 App／Web 使用；新客户端采用能力协商或明确的新版本契约，后端先部署。不能让旧 IPA 因协议更新失效。

### 4.3 异常行为

概览成功、细节失败时，保留概览并说明细节暂不可用，允许只重试细节。概览结束但列表未就绪时显示等待，不虚构点位。用户切源、换作品、结束或进入后台时取消相关待处理任务；迟到结果不得恢复旧会话。

验收：真实请求证明概览可在细节完成前发声；列表就绪即显示且不打断概览；手动选点优先；细节迟到不能重播概览。记录首音改善与总调用成本，模拟协议检查和真实 Gemini 联调分别报告。

## 5. 优化三：已登记二维作品的本地匹配与确认

### 5.1 范围与素材

先支持 3–5 幅常用二维画作，匹配和确认运行在 iPhone。此方案是建立参考图库，不是用几张图片训练新的分类模型。

每幅准备：清晰完整正面参考图、`artwork_id`、图像／内容版本、特征索引、经核对的内容和来源。若准备细节标注，保存参考图坐标及稳定 detail_id。另准备手机和眼镜拍摄的远近、倾斜、遮挡、反光视频以及陌生作品／相似画作作为验证集；视频中的连续近似帧不能冒充独立测试样本。

### 5.2 识别与几何校验

1. 从当前真实帧提取局部特征，与登记作品进行候选匹配。
2. 通过一致的几何变换及内点分布验证候选；检查投影区域有效、无退化、匹配不是集中在一小块重复纹理。
3. 用不同的新帧在本地确认同一作品及区域连续性，替代该路径的两次云搜索；仍保留多候选确认和不确定状态。
4. 匹配可靠后锁定作品，产出与现有识别管线兼容且注明来源的锁定上下文，进入概览／细节生成。
5. 低置信、像素不足、离开视野或陌生作品走云端回退；不能强制选最相似的一幅，也不能重复在本地和云端之间无限循环。

具体采用 ORB 或其他可维护的局部特征方案，在目标手机上对比速度、匹配率与内存后确定。几何采用平面投影，不把轴对齐框或图像分类概率当作完整透视定位。

本地路径必须显式使用 `recognition_method`（如 `local_reference`），不能伪造两次 Gemini 观察次数。后端相应校验登记 ID、版本、有效 ROI 与请求边界；设备上传的任意标签不得自动获得可信馆藏身份或来源权限。

### 5.3 缓存与追踪边界

- 可缓存已核对的概览、细节及音频，按作品、参考图版本、语言、内容版本和语音版本索引；前提是当前帧已可靠匹配到该作品。
- 缓存内容在界面标明为已准备资料；不把预标注直接宣称为现场新发现的细节。未登记作品仍走通用分析。
- 本地匹配得到的坐标可供手机追踪框使用，但当前 BUG-02 无框问题仍须独立定位；减少云调用不等于修复叠层。
- 镜片现实跟随框和相机到眼睛的光学映射仍是独立未完成项。此方案不支持任意 3D 物体视角变化。

验收：同一素材上本地锁定耗时与原云搜索比较；同时统计正确锁定、错误锁定、漏检、回退比例和云调用次数。出现更多错误作品锁定时不能以速度改善判定通过。

## 6. 优化四：消除逐句生成等待

### 6.1 推荐先按小节生成，流式播放

当前 `TourNarrator` 在一句音频播完后才推进到下一句并调用 Live。优先将生成单位改为当前小节：概览是一节，每个细节各是一节；一次发送该节已校验文本，收到 PCM 即开始播放，不等待整节音频全部生成。

将“音频生成单位”和“字幕显示单位”解耦：音频按小节流式播放，字幕仍按句显示。不能因为优化音频而回到逐字蹦字幕，也不能简单按固定秒数切字幕并声称精准对齐。

- 先只生成当前小节，避免用户改选后浪费整场导览音频。
- 依据实际播放时钟、转写事件与队列进度推进字幕；供应商未提供可靠句级时间戳时，记录同步误差，不伪造精确时间轴。
- 小节完成以音频真正播完为准，不以服务端 `turn_complete` 或最后一个包收到为准；防止末尾音频被下一节截断。
- 复用当前 Live 连接与上下文，不为正常句子边界重建会话。版本隔离和中断机制仍保留。

### 6.2 下一句／下一节预取作为后续选择

若分节流式方案仍有明显段间空白，再考虑只预取下一段。它不是直接在同一个 Live 会话发送两个并发轮次：当前代理只有一个 `playbackId`、待发文本和活动生成状态，必须先验证服务端能力并建立独立段队列。

预取内容只有播放权移交后才可出声；按 `session_epoch + artwork_version + section_id + playback_id + language + content_version` 关联。限制预取量、内存和生成预算，禁止无界音频缓冲。若需要第二个会话或其他音频生成接口，应另行评估并发、费用、音色一致性与取消机制，不在本轮默认为已可用。

### 6.3 打断、倍速与环形倒计时

- 用户讲话、选点、换作品或结束时立即停止旧播放，清除或失效旧段预取数据；迟到 PCM 不得重新播放。
- 暂停保留当前段实际播放位置；继续不重复已播放内容，不能被后台生成完成事件自动解除暂停。
- 播放倍速在本地音频处理生效；如果仅改变播放倍速，不必重新生成相同音频。测量实际输出时长变化。
- 为 PRD v0.4 的独立环形倒计时提供小节 ID、已播时长、总时长／估计状态。首包到达时通常还不知道完整音频长度，显示明确估计或待估算，不能把“当前已缓冲音频长度”当作整段总时长。
- 有语音播放但缺少可靠定位时继续遵循当前策略：隐藏无效框／局部窗，讲解继续；新点等待定位最多约 2.5 秒，不修改人工暂停优先级。

验收：固定文本对比分句方案与分节方案的首音、句间／段间空白；同时验证中英、六档倍速、每种中断位置、字幕可读性、旧音频隔离及内存上限。耳边听感与播放器指标单列。

| L4 | 分节流式音频与字幕调度 | TourNarrator、TourPresentation、NativeLiveVoice、Live 协议及播放队列 | 实际句间空白下降，打断／暂停／倍速／字幕与分段状态不退化 |
| L5 | 综合验收与交付记录 | 测试、运行记录、构建清单 | 区分模拟器、手机与眼镜结果，生成新 IPA 后才进入安装验收 |

各阶段独立提交、独立对照，出现回归可回退单项。先完成 L1，再根据实际最大瓶颈调整后续优先级；不要在同一轮同时换模型、调低识别门槛、改音频和改素材，导致结果不可解释。

## 8. 验收口径与交付物

以下为建议工程目标，待 L1 基线后确定数值，不是已有测试结果：

| 目标 | 建议验收口径 |
|---|---|
| 首次发声更快 | 同条件、同模型前后对比，主要演示路径首帧到首音中位数明显下降；暂以降低 30% 为工程目标，是否达到如实报告 |
| 概览不被细节阻塞 | 故意延迟细节响应，概览仍能播放；列表到达后立即显示且不中断概览 |
| 语音预连接有效 | Live 就绪与视觉分析确实重叠；不以收到连接事件代替听到声音 |
| 本地确认减少请求 | 登记作品可靠匹配的测试中，作品搜索云请求由通常至少两次降至零；统计回退和错误锁定，失败样本不剔除 |
| 连续朗读改善 | 同一文本下分别报告句间与段间空白中位数／最大值；打断、字幕和倍速不退化 |
| 用户控制保持有效 | 概览中选点、连续改选、暂停／继续、提问／继续、后台／重连不出现迟到内容或重复概览 |
| 内容与定位可靠 | 无可靠匹配不强行认作品；无来源不编造历史；无可靠框不展示陈旧位置 |

交付应包含：基线与改造后时间线、样本与版本清单、调用量／成本变化、失败与未到达测试、已知限制、可回退的源码提交。真实眼镜的麦克风、耳边输出和光学显示没有实测时明确留空。

本次提交只有本方案。上述性能目标、实现及验收全部待执行；二维追踪框 BUG-02 不因这份优化文档而关闭。
